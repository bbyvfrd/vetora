# Practice routes

How a route under `/api/p/:practiceId/…` is declared, what it may rely on, and how it is tested (#21; spec #18, "The request context"; spec 0001, "Tenancy and data topology"). Read it before adding one; the reviewer holds a new route to it (`CODING_STANDARDS.md`). The files are `src/http/practice-context.ts` (the middleware), `src/platform/request-context.ts` (`practiceContext()`), `src/platform/practice-registry.ts` (the registry cache) and `src/http/registration.ts` (the first four routes).

## Declaring one

- A practice route is a `createRoute` whose path starts `/api/p/{practiceId}/`, whose `middleware` is `[practiceRoute('<action>')]` with the action from the permission matrix in `packages/contracts` (`permissions`, `can()`), and whose `request` declares `params` from `PracticePath` (or a schema that extends it) and `headers: PracticeHeaders`, so the OpenAPI document names the `vetora-location` header and the web app's typed calls must send it (`practiceParams(me)` in `apps/clinic-web/src/api/practice.ts`).
- The action is declared where the route is, never checked in the handler: the middleware answers 403 before anything of the practice is read, and the web app hides what the same matrix refuses.
- The handler and the modules it calls read `{practice, location, actor, db, log}` from `practiceContext()`; a module's public interface takes no transaction argument. `db` is the request's one transaction, already `SET LOCAL ROLE` to the practice's role, `search_path` its schema and `ext`, `app.actor_id` the actor and `app.request_id` the request; the unqualified tables of `practice-schema.ts` resolve to that practice alone. Calling `practiceContext()` outside a practice route throws.
- Creates take a UUID v7 the client generates (`z.uuidv7()`: a `PUT` on the new id, or ids in the body) and, when the id is already there, write nothing and answer as the first request was answered (the breed as it stands, the registration's two ids), so a retry changes nothing. Names and phones travel in bodies; a search is a `POST`.
- A change to a versioned record (#22: the visit's note, Complete visit, Cancel visit) declares `headers: VisitChangeHeaders`, so `If-Match` carries the version the person read as an entity tag (`"3"`, `versionTag()`); the module's update matches the id and the version together and answers the new version, which the update trigger bumped, or 412 when no row matched and the record still stands. A state change (complete, cancel) is a `POST` on the record's path plus the verb. What the record's freeze refuses answers 409 naming the rule, from the database, never from a status check in the handler; the one status a module reads itself is a cancelled record's, which reads as gone (404) to every route.

## What the middleware answers

In order, each before the next is read: no session 401; not a member of the path's practice (or an id that is not a UUID) 403; the registry row's status not `active` 403; the practice's schema behind this code 503; no `vetora-location` header, or one that is not a UUID, 400; the route's action not among the actor's roles 403. Then the transaction opens, and a location that is not one of the practice's active locations answers 400 before the handler runs. None of these reaches a handler, so a refused write leaves no row and no audit row (`src/http/practice-context.test.ts`).

- **The registry cache** holds each practice's row for at most 30 seconds per process, with the newest migration its schema has recorded (`control.practice_schema_migration(id)`, an owner run function, since `vetora_app` has no grant on a practice schema). Nothing in the API changes the registry yet; a command that does runs in its own process, so the 30 seconds bound how late a running API sees it. Code that changes the registry in the API process, and a test that changes a practice's status, calls `forgetPractice(id)`.
- **Behind** means the schema's newest recorded migration sorts before the newest folder of `drizzle/practice` the image carries; a schema ahead of the code is served, since `migrate` runs before traffic switches and the two step rule keeps the outgoing image compatible.
- **The answer decides the transaction**: a status of 400 or more, or an error the handler threw, rolls it back; anything else commits. A rule the database refuses, at a statement (`app.onError`) or at `COMMIT` for a deferred check (the middleware), answers 409 with `code` naming the `vetora.*` rule (`ruleProblem()`); Postgres `detail`, `hint` and `where` never leave.
- **A known clash** a person can fix (a microchip already recorded) is caught by its constraint name with `violatedKeyOf()` and answered as a refusal of that field, shaped as the validation's issues are (`errors: [{ path, code, message }]`), which the web app maps to the field's message.

## Testing one

The API seam (`src/test-support.ts`): `provisionApiPractice()` gives a practice with its manager signed in, its default `locationId`, `addStaff()` for more logins, and `request(login, path, options)`, which prefixes `/api/p/<id>` and sends the location header (`location: null` sends none, `practiceId` another practice's id). Assert the status, the problem body and the rows through a migrator connection; a refusal leaves nothing. The database rules of a slice's tables are seam 1 (`src/platform/db/client-patient.test.ts` is the pattern: the audit row on every table, the missing actor, the constraints by name, a data migration in a new practice and in one migrated from before it).

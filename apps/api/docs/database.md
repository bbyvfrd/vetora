# Database conventions

How a change to the practice or control schema is written, guarded, and proven: the migrations, the tables and their registry entries, the actor and audit columns, the rule errors, the rule triggers, the deferred checks, and the database tests with the rules fixture. Read it before the first such change in a ticket; the reviewer holds the change to it (`CODING_STANDARDS.md`). The engine files are listed in [AGENTS.md](../AGENTS.md) (Key files, Commands); the design is spec 0002 (`docs/specs/0002-data-model/index.md`), and the rule IDs are `docs/domain.md` §8.

## Migrations

- Migrations are forward only and generated in order (`db:generate:*`), one folder per migration under `drizzle/<set>/`; a schema's pending migrations run in one transaction (a practice schema's together with its grants pass), so none may use `CREATE INDEX CONCURRENTLY`. drizzle-kit models tables only: extensions, functions, triggers, domains, and the control grants are written by hand into the generated `migration.sql`, each statement after a `--> statement-breakpoint` line (a domain goes before the first table that uses it); a new control table grants SELECT to `vetora_backup` there (dumps read everything). The migrate command exits 0 when current, 1 when the run did not complete (a schema's batch or its grants pass failed and the schema's transaction rolled back, `--practice` named an unknown slug, or the configuration or connection failed), 2 when another run holds the lock.
- A migration with no table change (functions, triggers, grants) is `pnpm --filter @vetora/api db:generate:practice --custom --name <name>`, an empty file to fill by hand; when the same ticket also changes a table, generate from the schema first and append the hand written SQL after a `--> statement-breakpoint`, or the folder has to be regenerated.
- Drizzle's `migrate()` creates the migrations schema before it runs the batch, so the control set's first migration says `CREATE SCHEMA IF NOT EXISTS "control"`; drizzle-kit generates a plain `CREATE SCHEMA`.
- drizzle-kit leaves a `customType` column's default unquoted (`DEFAULT AZN`): give those columns a `sql` default (`` sql`'AZN'` ``), as `platform-tables.ts` does.
- Drizzle 1.0 applies every folder a schema has not recorded, by name, whatever its timestamp (spec 0001's "Drizzle skips them silently" was 0.x; ADR 0002): a folder that lands with an older timestamp than one already landed is not lost, it runs first on a fresh schema and last on a migrated one, two orders for one set. `pnpm --filter @vetora/api db:check` refuses it (`drizzle-kit check` on both sets, then `src/platform/db/migration-order.ts`, which dates each folder by the first-parent commit that landed it; a folder generated and not committed yet counts as the newest); CI runs it with the full history (`fetch-depth: 0`), and a shallow clone is refused rather than read. Generate such a migration again rather than renaming it.

## Tables and the registry

- A practice table is declared without a schema (`platform-tables.ts`, or a module's `schema.ts`), uses the domain `customType`s from `domains.ts` for money and languages, spreads `standardColumns()` (whose two `staff_member` references stay unindexed, an exception to spec 0002's "foreign keys are indexed" that its comment records), and registers its class in `table-classes.ts` in the same commit (a view it adds goes in `views`, a function the practice role calls in `functions`): the grants pass gives the practice role exactly that class's privileges after every practice migration and never DELETE (IN-6), and refuses the schema's migration, batch and all, when a table has no entry or an entry no table. Its migration attaches the two shared triggers by hand, `set_updated_at` (BEFORE INSERT OR UPDATE) and `audit_row` (AFTER INSERT OR UPDATE OR DELETE), or the pass refuses it too; `audit_event` alone has neither. `vetora_app` holds no grant of its own on any practice table; a request reaches them only after `SET LOCAL ROLE p_<id>_role` (spec 0002, "Security model"; the request context arrives with slice 1).
- A table is declared where spec 0002's data model sketch assigns it: a module's `schema.ts` (`src/modules/README.md` says how a slice adds one), or `platform-tables.ts` for a platform table; `practice-schema.ts` gathers both for drizzle-kit and for `db()`, so a new table appears in `db().query` by itself. `schema.test.ts` compares the declarations with `control` and with a provisioned practice schema, table by table and column by column (type and nullability), so a column declared without its migration fails the suite (AC-1); it normalises Drizzle's spelling to `format_type()`'s (`numeric(10, 3)` is `numeric(10,3)`, `varchar(n)` is `character varying(n)`, and the array dimensions sit in `column.dimensions`, apart from `getSQLType()`).
- A practice migration that adds a table fails with `grants pass refused the schema, batch rolled back` until `table-classes.ts` names the table's class and the migration attaches both triggers; the log's `err.problems` lists every disagreement, the schema is as it was, so fix and rerun. The same refusal meets a migration that drops, disables, or changes one of the two triggers, drops a registered table, or a registry entry whose object a migration never created.
- A practice's schema and role names carry its UUID with hyphens (`p_019a…-…`), so psql needs the quotes: `set role "p_<id>_role"`, `select * from "p_<id>".practice_settings`; the code always goes through `pg.escapeIdentifier`.

## Actor and audit

- Every write names its actor (IN-1, AC-8): a request transaction sets `app.actor_id` to the staff member's id (`select set_config('app.actor_id', $1, true)`, beside `SET LOCAL ROLE`; `app.request_id` travels the same way), and the triggers fill `created_by`, `updated_by`, the clock columns, and `version` from it, never from the row sent, and write the `audit_event` row (`source = request`). A write with the actor unset or empty fails with `vetora.no_actor`. A `vetora_migrator` session writes without an actor but must name `app.migration`, which becomes `source = migration:<name>`: the commands set it on their connection, a data migration that writes rows sets its own folder name at its top (`select set_config('app.migration', '<folder>', true)`; a schema's pending migrations run in one transaction, so a writing migration that names nothing inherits the name of an earlier one in the batch), and a hand write in psql or a test sets it too, or `audit_event_actor_check` refuses the statement. The setting is ignored on any other session, so a request cannot pass as a migration.
- A hand write in psql needs an actor or a source, like any other: as the practice role `begin; set local role "p_<id>_role"; select set_config('app.actor_id', '<staff id>', true); insert …; commit;`, as the migrator `select set_config('app.migration', 'psql', true)` first; without, the practice role gets `vetora.no_actor` and the migrator a check violation on `audit_event_actor_check`. Once a transaction has set `app.actor_id`, the session reads it back as `''` rather than unset; the triggers treat both as missing.
- `provision-practice` writes the first manager only while the practice has no staff, and a rerun writes any missing seed row as the practice's first manager, so a rerun changes nothing and completes nothing in another name whichever `--manager-user-id` it is given; the staff sync of slice 1 adds the rest.

## Rule errors

- A rule the database enforces raises `RAISE EXCEPTION USING MESSAGE = 'vetora.<rule>: …', ERRCODE = 'VT0nn'`: the message starts with the rule name, the SQLSTATE is a five character code in the `VT` class, one per rule (the deferred checks share `VT005` and name their rule in the message), and `errors.ts` lists them so a handler maps a failed statement or commit to a problem detail by code (`ruleOf()`, `missingRowOf()`); the message never carries personal data. The owner run functions are `SECURITY DEFINER`, owned by `vetora_migrator`, `search_path = pg_catalog`, tables addressed through `TG_TABLE_SCHEMA`, and not executable by PUBLIC.

## Rule triggers

- The rule triggers (spec 0002, "Interface surface"; the practice set's `rules` migration) are generic functions driven by their trigger arguments, never one per table, and they hold for every role, the owner included (a migration that must change a frozen row disables the trigger for its own statement, in the migration file). `set_once('col', …)` BEFORE UPDATE on a set once class table: each named column goes from null to a value once and nothing else changes; `set_once('only', 'col', …)` watches the named columns alone, for a set once column on a mutable table (`practice_settings.go_live_at`). `freeze_record('status', 'final, values', 'allowed, cols')` BEFORE UPDATE OR DELETE on a frozen by status table: once the status is final only the allowed columns change and DELETE is refused. `lock_parent('parent_table', 'fk_col', 'status', 'final, values')` BEFORE INSERT OR UPDATE OR DELETE on a child: the parent row is read `FOR SHARE`, so a child written during a freeze waits for it and is then refused, and a handler that freezes a parent locks it `FOR UPDATE` before it reads the children it validates; the share lock has a cost the spec accepts, so a transaction that adds children and then updates the parent takes that `FOR UPDATE` lock before the inserts, or two such transactions deadlock on it. `assert_backdate_limit()` (the ticket's name; the `assert_` prefix otherwise belongs to the deferred checks) BEFORE INSERT OR UPDATE on every event table beside the table's CHECK `occurred_at <= now()`: the window is `practice_settings.backdate_limit_hours`, measured when `occurred_at` is written or moved. Lists are comma separated strings; a misspelt column name fails the first write loudly, a misspelt status value does not (the table's CHECK is not consulted), which the slice's test seam is for; `updated_at`, `updated_by`, and `version` never count as a change (BEFORE triggers fire in name order, all of these before `set_updated_at`).

## Deferred checks

- A deferred check (RX-3, IN-3: companion rows or no commit) is a per rule function `assert_<rule>()`, written by the slice that owns the rule, run by `CREATE CONSTRAINT TRIGGER assert_<rule> AFTER INSERT OR UPDATE … DEFERRABLE INITIALLY DEFERRED FOR EACH ROW`, raising `vetora.incomplete_<rule>: <missing row>` with `INCOMPLETE_RULE_CODE`; the function reads the row by id as it stands at commit, because a deferred trigger is handed the row as the event wrote it and an insert followed by an update would otherwise be checked on the stale version. It surfaces at COMMIT, not at the failing statement, and rolls the whole transaction back: a handler treats a commit failure as a first class error and maps it with `ruleOf()` and `missingRowOf()`. The worked example is the rules fixture's `assert_fixture_companion()` in `test-support.ts`.

## Database tests

- Database tests (`migrator.test.ts`, `provisioning.test.ts`, `audit.test.ts`, `grants.test.ts`, `rules.test.ts`, and the parity cases of `schema.test.ts`) run when `DATABASE_URL_MIGRATOR` and `DATABASE_URL_DIRECT` are set (`vitest.config.ts` loads the workspace `.env`; CI sets them after `docker compose up -d --wait postgres`) and are skipped otherwise. They use `vetora_test`, created by the compose init script with the same grants as `vetora` and emptied by the `globalSetup` before each run, so they never touch `vetora`'s schemas; roles are cluster wide, so the reset drops only the `p_*_role` of a `p_*` schema it found in `vetora_test`. The test files run one after another (`fileParallelism: false`) because they share that database. A test that needs a practice takes one from `provisionTestPractice()` and drops it afterwards; request transactions go through `asPractice()` from `test-support.ts` (a `vetora_app` connection, `SET LOCAL ROLE`, `app.actor_id` the practice's manager unless the case says otherwise, committed unless `run` throws); a migrator connection that writes practice rows by hand names `app.migration` once per session. With `CI` set, missing variables fail the setup instead of skipping the suite. A trigger or constraint is proven with the rules fixture, `createRulesFixture(urls, practice)` (its three tables and what each proves are in its JSDoc): created and granted by class as a migration would be, committed so that `vetora_app` connections see them, removed by `drop()`. A slice proves its own trigger the same way, through `asPractice()` for what a request sees and the migrator for the owner's side; a concurrency case opens a transaction with `beginAsPractice()` on a second `vetora_app` connection, waits on `pg_blocking_pids()` until the other blocks, and then releases it.
- A `migrate` run (the command, or another test file's `beforeAll`) refuses a practice schema that still holds the rules fixture (`table "fixture_record" has no class in table-classes.ts`): `drop()` the fixture, or the practice, first.
- Two checkouts cannot share `vetora_test`: the global setup empties it and a practice's role is cluster wide, so a second session (a worktree for another ticket) runs its own compose project on another port and points its `.env` at it.
- A compose volume created before `vetora_test` existed lacks it: `pnpm local:down -v`, then `pnpm local:up` reruns the init script (the local `vetora` data goes with it).
- `pg` parses a `text[]` result but hands a `name[]` back as a string: cast catalog names to text (`t.tgname::text`) in a query a test asserts on.
- A grants pass revokes and grants again, which moves the practice role's item to the end of each ACL array: compare ACLs as sorted sets (`unnest`, then `array_agg(item::text order by item::text)`), as `grants.test.ts` and `rules.test.ts` do, never as `relacl::text`.

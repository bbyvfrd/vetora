# apps/api

## Overview

The vetora API: a Hono server on Node 24 that declares every route with a zod schema from `@vetora/contracts`, publishes its OpenAPI document, and reaches Postgres through Drizzle. It grows into a modular monolith with one module per bounded context under `src/modules/` (spec 0001); the same image carries the `migrate` and `provision-practice` commands (`dist/migrate.js`, `dist/provision-practice.js`) and later the worker.

## Stack

- Hono 4 on `@hono/node-server`, routes through `@hono/zod-openapi` 1, zod 4 from the pnpm catalog
- Drizzle ORM 1.0 (pinned exactly to its release candidate) over `pg`, against Postgres 18
- pino for logs, `@sentry/node` 11 for error reports, tsx in development, plain `tsc` for the build (ESM, NodeNext)
- Shipped as a Docker image built from the repository root (`Dockerfile`, Turborepo prune) and rolled out with Kamal (`config/deploy.yml` plus a destination file per environment)

| `src/index.ts` | Startup: imports `instrument.js` first, validates the config, serves on `0.0.0.0`, and stops cleanly on SIGTERM and SIGINT (10 s cap) |
| `src/app.ts` | The `OpenAPIHono` app: request id and request log middleware, `/up`, `/api/health`, `/api/openapi.json`, the 404 and 500 handlers |
| `src/openapi.ts` | Writes the OpenAPI document to `packages/contracts/openapi.json` (run as `pnpm openapi` at the root) |

| `src/provision-practice.ts` | The `provision-practice` command: parses `--slug`, `--name`, `--manager-user-id`, `--manager-name`, `--location-name`, `--time-zone`, `--languages`, validates them with the zod schema in `provisioning.ts`, prints the practice id; exit codes 0 (provisioned, a rerun included), 1 (slug held under another name, invalid argument, or a step failed), 2 (lock held) |

| `src/http/` | Route declarations (`createRoute`) and HTTP middleware |
| `src/platform/config.ts` | The zod validated environment behind `loadConfig()` (the API) and `loadMigratorConfig()` (the commands); a `ConfigError` names the missing variables, never their values |

| `src/platform/db/migrator.ts` | The migrate engine: one direct `pg.Client` as `vetora_migrator`, the advisory lock (`MIGRATE_LOCK_KEY`), the control set through Drizzle's `migrate()` with `control.__drizzle_migrations` as the truth, then the practice loop: every `control.practice` row in registry order (`created_at`, `id`), or the one `--practice` names, each through `migratePractice()` (one transaction per schema: `search_path` set locally to the schema and `ext`, `migrationsSchema` the schema, Drizzle's batch nested as a savepoint, the grants pass after it, committed together or rolled back together); the loop stops at the first failure with the earlier schemas migrated. | `src/platform/db/provisioning.ts` | The provision engine behind `provision-practice`: under the migrate lock, in order and each idempotent, the registry row (status `provisioning`, a UUID v7 id, `schema_name` `p_<id>`, `role_name` `p_<id>_role`) → the NOLOGIN role and `vetora_app`'s membership (`INHERIT FALSE, SET TRUE`) → the schema → `migratePractice()` → the first manager's `staff_member` row (`roles = {manager}`, only while the practice has no staff), `practice_settings`, and the default `location`, each inserted only when missing and written as the manager (`app.migration = provision-practice` and `app.actor_id` = the manager on the connection, so all three carry the manager as `created_by` and in `audit_event`) → status `active`; a slug held under another name changes nothing. `provisionInput` is the zod schema for the arguments |
| `src/platform/db/grants.ts` | The grants pass, run by `migratePractice()` inside every practice schema's migration transaction for both commands: it reads the live catalog, refuses the schema with a `TableClassMismatch` naming every problem (a table with no class, a view with no entry, an entry with no object behind it, a table other than `audit_event` whose `set_updated_at` or `audit_row` trigger is missing, disabled, running another function, or firing on other events, an entry naming a column the table lacks), then `REVOKE ALL` on the schema and on every table, sequence, and routine in it from the practice role, PUBLIC, and `vetora_app`, and grants the class's privileges per table (`grantOf()`), column level for `set_once` and `noUpdate`, SELECT on the registered views, EXECUTE on the registered functions, USAGE on the schema and `ext` for the practice role, and `vetora_backup` USAGE and SELECT on everything; idempotent, committed with the batch or not at all; returns what it granted for the log |
| `src/platform/db/table-classes.ts` | The table class registry (`tableClassRegistry`): every practice table names its class here (`append_only` INSERT and SELECT; `set_once` INSERT and SELECT plus UPDATE on its `setOnce` columns; `mutable` and `frozen_by_status` INSERT, SELECT, UPDATE, less any `noUpdate` columns; `function_written` SELECT), beside the `views` the practice role reads and the `functions` it calls; `grantOf()` turns an entry into the table level privileges and the column level UPDATE. A module registers its tables, views, and callable functions here in the commit that adds its schema. `audit_event` is the function written table without the shared triggers (`AUDIT_LOG_TABLE`); `MIGRATIONS_TABLE` names Drizzle's table, the one outside the registry |
| `src/platform/db/platform-tables.ts`, `domains.ts` | The practice schema's platform tables declared without a schema: `practice_settings` (one row behind a constant id), `location` (one default per practice), `staff_member` (the actor every write names, `id` = the control user id, `roles` a non empty subset of the five in `STAFF_ROLES`), `audit_event` (one row per insert, update, delete, written only by `audit_row()`); `standardColumns()` is the `created_at`, `created_by`, `updated_at`, `updated_by`, `version` every table but `audit_event` spreads; and the `customType`s for the SQL domains `minor_units`, `currency_code`, `lang_code`. Every export of both files is tagged `@public`, so a module's `schema.ts` may import it (Conventions, module boundaries) |
| `src/platform/db/errors.ts` | The rule errors the database raises, each `vetora.<rule>` with its SQLSTATE in the `VT` class (`vetora.no_actor` `VT001`, `vetora.set_once` `VT002`, `vetora.frozen_record` `VT003`, `vetora.backdated_too_far` `VT004`, and the deferred checks' family `vetora.incomplete_<rule>`, every member on `INCOMPLETE_RULE_CODE` `VT005`), `ruleOf()`, which maps a failed query or commit to its rule by the code at the root of the cause chain (a deferred check by the rule name in its message), and `missingRowOf()`, the companion row a failed commit names |

## Commands

```bash
pnpm --filter @vetora/api dev         # node --watch through tsx, reads .env; needs pnpm local:up at the root
pnpm --filter @vetora/api build       # tsc -p tsconfig.build.json to dist/, tests left out
pnpm --filter @vetora/api typecheck
pnpm exec vitest run --project @vetora/api   # at the root; pnpm test runs every workspace
pnpm exec vitest run --project @vetora/api apps/api/src/rehearsal.test.ts   # the two practice rehearsal through the commands, whole: its cases are one walk
pnpm openapi                          # at the root: builds, writes openapi.json, regenerates the contracts types
pnpm --filter @vetora/api migrate     # reads .env when present; the control set, then every practice schema in registry order, the grants pass inside each schema's transaction; --dry-run lists and changes nothing, --practice <slug> limits the loop
pnpm --filter @vetora/api provision-practice -- --slug alfa --name "Alfa Vet" --manager-user-id <uuid> --manager-name "Dr Aliyeva" --location-name "Nərimanov"   # [--time-zone Asia/Baku] [--languages az,ru], the first language is the default; prints the id; safe to rerun
pnpm --filter @vetora/api db:generate:control --name <name>   # after editing control-schema.ts; finish the SQL by hand
pnpm --filter @vetora/api db:generate:practice --name <name>  # after editing the platform tables or a module's schema.ts; the migrate command applies it to every practice
pnpm --filter @vetora/api db:check    # drizzle-kit check on both sets, then the order check (migration-order.ts): a folder out of order fails; CI runs it with the full history
docker compose exec postgres psql -U vetora_app -d vetora   # at the root; there is no local psql (-U vetora_migrator, -d vetora_test as needed)
DATABASE_URL_MIGRATOR=postgres://vetora_migrator:vetora_migrator@localhost:5432/vetora_test pnpm --filter @vetora/api migrate   # a shell variable wins over .env: a command against vetora_test
kamal deploy -c apps/api/config/deploy.yml -d staging   # at the root; a destination is always required
```

## Conventions

- A route is a `createRoute` declaration whose schemas come from `@vetora/contracts`, never an inline shape; the API serves its routes under `/api` itself (kamal-proxy keeps the prefix, Vite proxies it in development).
- Every error is problem details JSON through `problem()`: 400 for validation (the `defaultHook`), 404 from `notFound`, 500 from `onError`, which scrubs the error, logs it with the request id, and reports it to Sentry.
- Modules reach each other only through their public interface or domain events, never through each other's tables; only `src/platform/` may import a database client (spec 0001, "Repository layout"). Biome enforces both: `pg` and `drizzle-orm/node-postgres` import only under `src/platform/` (`noRestrictedImports`), and inside `src/modules/` a module's `index.ts` is its public interface while every other export, its `schema.ts` included, is visible only within that module's folder (`noPrivateImports`, package visibility). The same rule reads a platform export as package private unless it is tagged `@public`: the platform tables and the domains carry the tag, so a module's `schema.ts` imports them; a new platform export a module needs gets the tag, not an override. A foreign key to another module's table is a plain `uuid` column in TypeScript (`.references()` only inside the module and to the platform tables); the migration carries the `REFERENCES`, so the database enforces the key and the lint rule keeps the boundary. `db().query` names every table of both schemas, so the import rule, not the type, is the boundary: a module's code reaches its own tables and the platform's.
- Database work follows [docs/database.md](docs/database.md): a migration, a table and its registry entry, a trigger or a deferred check, a hand write in psql, or a database test; read it before the first such change in a ticket, and `CODING_STANDARDS.md` holds the change to it at review.
- Request code runs through the pooler in transaction mode: no session state beyond `SET LOCAL`, no named prepared statements, no advisory locks. `direct()` is for LISTEN and the worker; the commands open their own `pg.Client` on `DATABASE_URL_MIGRATOR`.
- The commands log ids, slugs, schema and role names, counts, and durations: never a practice's name, address, phone, or tax id, which spec 0002 lists as personal data.
- One JSON log line per request (method, path, status, duration, request id), never a body or a query string; `/up` is not logged.
- A new configuration variable goes into the zod schema in `config.ts`, into `.env.example`, into `config/deploy.yml` (`env.clear` or `env.secret`), and, when secret, into `.kamal/secrets-common`.
- Relative imports end in `.js` (NodeNext ESM with `verbatimModuleSyntax`); there is no bundler.
- Tests sit beside the code as `*.test.ts`: `tsconfig.json` (typecheck) includes them, `tsconfig.build.json` (build) leaves them out of `dist/`, and `vitest.config.ts` here silences the logger while they run. A helper two test files need lives in `test-support.ts`, in one place.

## Gotchas

- `/up` is the liveness route for kamal-proxy and the uptime check: cheap, no database. `/api/health` is the one that touches the database.
- `instrument.ts` stays the first import of `index.ts`, or Sentry misses errors; without `SENTRY_DSN_API` it does nothing, which is the local setup.
- A route change changes the contract: run `pnpm openapi` and commit `packages/contracts/openapi.json` and `src/generated/api.ts`, or CI fails. The document's `info.version` is fixed at `0.1.0` so the committed file does not change per deploy.
- `@vetora/contracts` resolves from its `dist/`: rebuild it after editing a schema (`pnpm --filter @vetora/contracts build`); `dev` does not watch packages.
- Drizzle is `1.0.0-rc.5` while npm `latest` is still 0.45: bump only after reading the changelog, with `drizzle-kit` on the same version. The rc wraps a failed query in a `DrizzleQueryError` whose `cause` is the Postgres error and whose `params` are the request's values: read `cause.code`, and let `scrubError()` see the whole chain (it drops the params from the message, the stack, and the object before anything is logged or reported).
- A `noPrivateImports` error in a module on an import from `src/platform/` means the export lacks its `@public` tag: add the tag, not an override.
- `pnpm run <script> -- --flag` hands the `--` on to node, which passes it to the script; `migrate` and `provision-practice` drop a leading `--`, so both forms work.
- The Dockerfile sets `CI=true`, so `pnpm install` inside the image build skips lefthook's hook installation (the build context has no git repository).
- The Kamal destination files hold placeholders (`STAGING_DROPLET_IP`, `staging.vetora.example`) until `infra/digitalocean.sh` has run, and the staging workflow stays inert until the `STAGING_READY` repository variable is set.
- The local database (the reset with `pnpm local:down -v`, `vetora_test` and the tests that empty it, how a throwaway or hand provisioned practice is dropped) is [docs/database.md](docs/database.md), Database tests; `docs/specs/0002-data-model/verify.md` is the walk that provisions practices in `vetora` by hand, with its Clean up.

## 1. git worktree (git 2.54.0)

**Findings**

- One branch in one worktree: `add` "refuses to create a new worktree when `<commit-ish>` is a branch name and is already checked out by another worktree" (`--force` overrides). The error comes from `die_if_checked_out()` in `branch.c`: `fatal: '<branch>' is already used by worktree at '<path>'`. Observed: `git worktree add <scratch path> feat/12-app-shell` printed `fatal: 'feat/12-app-shell' is already used by worktree at '/Users/faridbabayev/projects/personal/vetora'`, exit 128, and created nothing. The same function guards `git checkout` and `git switch` (`builtin/checkout.c`, skipped only by `--ignore-other-worktrees`), and `git branch -d` refuses a branch "used by worktree at" a path (`builtin/branch.c`).
- The commands. `add <path> [<commit-ish>]` creates the directory and checks the commit out; with no commit-ish it creates a branch named after `basename <path>` from `HEAD`, or checks that branch out if it exists and is free; `-b`/`-B` name the branch, `-d` detaches, `--no-checkout` skips the checkout, `--lock [--reason <string>]` keeps the new worktree locked without a race. `list` prints the main worktree first, then each linked one with `locked` and `prunable` annotations; `--porcelain` gives one attribute per line (`worktree`, `HEAD`, `branch`, `locked [reason]`, `prunable`). `lock`/`unlock` write and delete a `locked` file in the worktree's entry ("The file contains the reason in plain text"); a locked worktree can't be pruned, moved, or removed. `move` relocates a linked worktree (never the main one). `prune` removes `$GIT_DIR/worktrees` entries "whose working trees are missing"; `git gc` prunes them after `gc.worktreePruneExpire`, default `3.months.ago`. `repair` reconnects moved checkouts.
- `remove`: "Only clean worktrees (no untracked files and no modification in tracked files) can be removed. Unclean worktrees or ones with submodules can be removed with --force"; a locked one needs `--force` twice. The exact messages in `builtin/worktree.c`: `'<path>' contains modified or untracked files, use --force to delete it`, `cannot remove a locked working tree, lock reason: <reason>` followed by `use 'remove -f -f' to override or unlock first`, and `'<path>' is a main working tree`. `remove` deletes the directory and the worktree's entry under `.git/worktrees` (`delete_git_dir()`); it never touches the branch. A `node_modules` or `.env` left in the worktree counts as untracked, so a worktree that was used needs `--force`.
- The `.git` file: "Within a linked worktree, $GIT_DIR is set to point to this private directory (e.g. /path/main/.git/worktrees/test-next in the example) and $GIT_COMMON_DIR is set to point back to the main worktree's $GIT_DIR (e.g. /path/main/.git). These settings are made in a .git file located at the top directory of the linked worktree." Observed: the file holds exactly `gitdir: /Users/faridbabayev/projects/personal/vetora/.git/worktrees/prototype+better-auth`, and that entry holds `HEAD`, `index`, `ORIG_HEAD`, `logs/`, `refs/`, `commondir` (`../..`), `gitdir` (the path back to the worktree's `.git` file), `locked`, and Claude Code's marker `CLAUDE_BASE` (the base commit, `379d0fc`).
- Shared and private. A linked worktree shares "everything except per-worktree files such as HEAD, index, etc."; refs under `refs/` are shared except `refs/bisect`, `refs/worktree`, `refs/rewritten`; the config file is shared by default. Hooks live in `$GIT_DIR/hooks` resolved through the common dir: `githooks(5)` says "By default the hooks directory is $GIT_DIR/hooks, but that can be changed via the core.hooksPath configuration variable", and `git rev-parse --git-path hooks` run inside the linked worktree returns `/Users/faridbabayev/projects/personal/vetora/.git/hooks` (observed; `--git-path info` likewise returns the shared `.git/info`). One hook set serves every worktree. Git runs a hook with the worktree's root as its working directory, so a hook sees the committing worktree's files.
- Untracked and ignored files: `add` checks the commit out, so a new worktree holds tracked files only; `.env`, `node_modules/`, `.turbo/`, `dist/` have to be recreated. The man page says this only through "checkout <commit-ish> into it"; Claude Code's docs say it outright ("A worktree is a fresh checkout, so untracked files like `.env` or `.env.local` from your main repository are not present"). Observed: both linked worktrees got their `apps/api/.env` and `node_modules` minutes after creation, by hand or by a setup script.
- Per worktree configuration: `git config extensions.worktreeConfig true`, then `git config --worktree` reads and writes `$GIT_DIR/config.worktree` (`.git/worktrees/<id>/config.worktree`, "read after .git/config is"); `--worktree` without the extension "is the same as --local". "Older Git versions will refuse to access repositories with this extension", and `core.bare`/`core.worktree` lose their main worktree exception. Claude Code's `worktree.sparsePaths` turns this extension on in the shared `.git/config` (section 9).
- Deleting the branch after a merge: the man page's example commits in the linked worktree, runs `git worktree remove ../temp`, and leaves the branch for merging. Afterwards `git branch -d <branch>` ("The branch must be fully merged in its upstream branch, or in HEAD if no upstream was set"), `-D` to force; the worktree goes first, because git refuses to delete a branch a worktree still holds.
- "Multiple checkout in general is still experimental, and the support for submodules is incomplete" (BUGS).

**Source**: `man git-worktree`, `man git-config` (`--worktree`, `extensions.worktreeConfig`, `core.hooksPath`, `gc.worktreePruneExpire`), `man githooks`, `man git-branch` of the installed git 2.54.0 (page footer "Git 2.54.0, 2026-04-19"); the same text is at https://git-scm.com/docs/git-worktree and https://git-scm.com/docs/git-config. Error strings from https://github.com/git/git/blob/v2.54.0/builtin/worktree.c, `branch.c`, `builtin/branch.c`, `builtin/checkout.c` (read 2026-10-26).

**Confidence**: high.

## 2. pnpm 10.33.0

**Findings**

- The store is one per disk: `storeDir` defaults to `$PNPM_HOME/store` or `$XDG_DATA_HOME/pnpm/store` when set, else `~/Library/pnpm/store` on macOS, `~/.local/share/pnpm/store` on Linux, `~/AppData/Local/pnpm/store` on Windows. Observed: `pnpm store path` is `/Users/faridbabayev/Library/pnpm/store/v10`. "All the files are saved in a single place on the disk. When packages are installed, their files are hard-linked from that single place, consuming no additional disk space. This allows you to share dependencies of the same version across projects." "The store should be always on the same disk on which installation is happening"; from another disk pnpm copies instead of hard linking. So a second `pnpm install --frozen-lockfile` in a worktree resolves from the committed lockfile and hard links everything the main checkout already fetched; `--offline` restricts it to the store ("If a package won't be found locally, the installation will fail").
- `--frozen-lockfile`: "Default: For non-CI: false; For CI: true, if a lockfile is present"; "If true, pnpm doesn't generate a lockfile and fails to install if the lockfile is out of sync with the manifest / an update is needed or no lockfile is present."
- `node_modules` is per directory: each checkout gets its own tree (observed: both worktrees hold a real `node_modules` directory). Nothing but the store is shared.
- `onlyBuiltDependencies` (10.x): "A list of package names that are allowed to execute preinstall, install, and/or postinstall scripts during installation. Only the packages listed in this array will be able to run those lifecycle scripts." pnpm 11 removed it: "The following settings have been removed in v11 and replaced by allowBuilds: onlyBuiltDependencies, onlyBuiltDependenciesFile, neverBuiltDependencies, ignoredBuiltDependencies, and ignoreDepScripts" (read before a major bump).
- Whether a worktree's install reruns lefthook's postinstall: `sideEffectsCache` (default `true`) is "Use and cache the results of (pre/post)install hooks. When a pre/post install script modify the contents of a package (e.g. build output), pnpm saves the modified package in the global store. On future installs on the same machine, pnpm reuses this cached, prebuilt version", with the note to disable it when "The install scripts modify files outside the package directory (pnpm cannot track or cache these changes)" or "perform side effects that are unrelated to building the package". lefthook's `postinstall.js` runs `lefthook install` (skipped when `CI` is set unless `LEFTHOOK` is set too), which writes `.git/hooks/*` and `.git/info/lefthook.checksum`, both outside the package. Observed: the store index `~/Library/pnpm/store/v10/index/df/…-lefthook@2.2.2.json` carries a `sideEffects` entry keyed `darwin;arm64;node24;deps=…`, so a later install on this machine can restore the cached (unchanged) package instead of running the script. The docs do not say in words that a cached entry skips the script, so a rerun in a worktree is not guaranteed; the hook files are shared through the common dir anyway (section 1), so nothing is missing either way, and `pnpm exec lefthook install` is the explicit command (the comment in `lefthook.yml` already names it).
- Worktrees and multiple checkouts: not documented (settings, store settings, build settings, `pnpm install`, motivation, FAQ, and node_modules structure pages checked).

**Source**: https://pnpm.io/10.x/settings (`storeDir`, `onlyBuiltDependencies`, `sideEffectsCache`), https://pnpm.io/10.x/cli/install (`--frozen-lockfile`, `--offline`, `--ignore-scripts`), https://pnpm.io/motivation, and the current https://pnpm.io/settings, https://pnpm.io/settings/store, https://pnpm.io/settings/build for the v11 and v12 changes, read 2026-10-26; the installed `node_modules/lefthook/postinstall.js` (2.2.2).

**Confidence**: high for the store and the lockfile; medium for the postinstall question.

## 3. Turborepo 2.11.10

**Findings**

- Local cache: "Turborepo stores the results of tasks in the `.turbo/cache` directory on your machine"; `cacheDir` defaults to `".turbo/cache"`; `--cache-dir <path>` and `TURBO_CACHE_DIR` ("Sets the cache directory, similar to using --cache-dir flag") change it ("Ensure the directory is in your .gitignore when changing it"). `node_modules/.cache/turbo` appears on none of the pages read; observed: only `.turbo/cache` exists here, with 320 entries.
- Worktrees are documented, and the cache is shared: "When working with Git worktrees, Turborepo automatically shares the local filesystem cache between the main worktree and any linked worktrees … When you create a linked worktree with git worktree add, Turborepo detects this configuration and automatically redirects the cache to the main worktree's .turbo/cache directory." The run prints "• Remote caching enabled, using shared worktree cache". "If you set an explicit cacheDir in your turbo.json, worktree cache sharing is disabled and each worktree will use its own cache directory as specified." Caveat: "Cache artifacts are restored without rewriting their contents. If a task output contains the absolute path to its worktree, sharing that artifact can restore an output that points to another checkout. Set an explicit cacheDir, such as .turbo/cache, to keep the local cache isolated to each worktree." Observed: neither linked worktree has a `.turbo` directory, and the main `.turbo/cache` gained entries at 01:42 while a worktree session was building, so the sharing is active in this repo.
- The daemon: "Deprecated: The daemon is no longer used for turbo run and this option will be removed in version 3.0. The --daemon and --no-daemon flags are also deprecated. The daemon is still used by turbo watch and the Turborepo LSP." Observed: `turbo daemon status` reports it is not running. Two roots therefore do not meet in a daemon for `turbo run`; whether `turbo watch` daemons of two roots conflict is not documented on the pages read (the dedicated `reference/daemon` page returned no content).
- `--affected` "is equivalent to --filter=...[main...HEAD]", "The comparison requires everything between base and head to exist in the checkout", overridable with `TURBO_SCM_BASE` and `TURBO_SCM_HEAD`; a linked worktree has its own `HEAD` and shares `main`, so it works per worktree. The `turbo ls` and `turbo prune` pages say nothing about worktrees (`prune` mentions only "Respect .gitignore file(s) when copying files to the output directory").
- `envMode` default `"strict"`: "Filter environment variables to only those that are specified in the env and globalEnv keys in turbo.json". A per checkout variable such as a port that a task needs must be read from a file by the task (Vite's `loadEnv`, Node's `--env-file`) or listed under `env`/`globalEnv`; a value exported in the shell alone does not reach `turbo run dev`.

**Source**: https://turborepo.com/docs/crafting-your-repository/caching ("Git Worktree Cache Sharing"), https://turborepo.com/docs/reference/configuration (`cacheDir`, `daemon`, `envMode`), https://turborepo.com/docs/reference/system-environment-variables, https://turborepo.com/docs/reference/run (`--affected`, `--cache-dir`, `--daemon`), https://turborepo.com/docs/reference/ls, https://turborepo.com/docs/reference/prune, read 2026-10-26 (the pages document 2.x without a version stamp; local turbo 2.11.10).

**Confidence**: high for the cache; medium for the daemon.

## 4. Docker Compose v5.0.2

**Findings**

- Project name precedence, highest first: 1 the `-p` flag; 2 `COMPOSE_PROJECT_NAME`; 3 "The top-level `name:` attribute in your Compose file. Or the last `name:` if you specify multiple Compose files"; 4 "The base name of the project directory containing your Compose file. Or the base name of the first Compose file" given with `-f`; 5 the base name of the current directory when no file is specified. Names hold only lowercase letters, digits, dashes, underscores, and start with a letter or digit. "Compose uses a project name to isolate environments from each other", for example "On a development host: Create multiple copies of a single environment, useful for running stable copies for each feature branch of a project." A defined name "is exposed for interpolation and environment variable resolution as COMPOSE_PROJECT_NAME". `COMPOSE_PROJECT_NAME` "does the same as the -p flag"; "If flags are explicitly set on the command line, the associated environment variable is ignored."
- Which `.env` is read for interpolation: "1 Variables from your shell environment; 2 Variables from a file set by --env-file; 3 If --env-file is not set, variables from an .env file in the project directory, where the project directory is: --project-directory if set; otherwise, the directory of the first Compose file specified with -f/--file; otherwise, your shell's current directory (PWD)". That file "loads values both for self-configuration and interpolation", so it can set `COMPOSE_PROJECT_NAME` and `COMPOSE_FILE` too. `--env-file` paths are "relative to the current working directory where the Docker Compose command is executed"; several `--env-file` flags are read in order and later files override; a missing file errors with `Couldn't find env file`. `docker compose config --environment` lists what Compose will use.
- Syntax: `${VAR:-default}` ("value of VAR if set and non-empty, otherwise default"), `${VAR-default}` (set, else default), `${VAR:?error}` ("value of VAR if set and non-empty, otherwise exit with error"), `${VAR?error}` (set, else exit with error), `${VAR:+replacement}`, `${VAR+replacement}`; nesting such as `${VARIABLE:-${FOO:-default}}` works; `$$` is a literal dollar. An unresolved variable without a default "displays a warning and substitutes the variable with an empty string". Interpolation runs per file before merging, on values only.
- Files: "By default, Compose reads two files, a compose.yaml and an optional compose.override.yaml file"; `-f` files merge "in the order they're specified on the command line. Subsequent files may merge, override, or add to their predecessors"; "Paths are evaluated relative to the base file" (the first `-f`); `COMPOSE_FILE` equals `-f`; `--project-directory` is "an alternate working directory (default: the path of the, first specified, Compose file)". Merge rules: mappings merge key by key, sequences append, except the "unique resources" `ports` (key `{ip, target, published, protocol}`), `volumes`, `secrets`, `configs` (key `target`), where "Compose appends new entries that do not violate a uniqueness constraint and merge entries that share a unique key". `!reset` removes a value (`ports: !reset []`, `FOO: !reset null`); `!override` "allows you to fully replace an attribute, bypassing the standard merge rules" ("Requires: Docker Compose 2.24.4 and later"), for example `ports: !override` followed by `- "8443:443"`, "If !override had not been used, both 8080:80 and 8443:443 would be exposed".
- Volumes: a named volume is created as `{project_name}_<key>` unless `name:` sets a custom name ("The name is used as is and is not scoped with the stack name") or `external: true` ("Compose then doesn't create the volume and returns an error if the volume doesn't exist"). A new project name therefore starts with an empty `postgres-data`, and the image's init scripts run again (section 5). Observed: `vetora_postgres-data`, `vetora_s3-data`.
- Verified locally by the coordinating session on 2026-10-26 with Compose v5.0.2: a `.env` in the project directory that sets `COMPOSE_PROJECT_NAME` beats a top level `name:` in the file, while a shell variable beats the `.env`; `${VAR:?message}` in `name:` and in a published port fails with that message when the variable is missing; named volumes are prefixed with the project name (`vetora-s2_postgres-data`), so a new project starts with an empty volume.
- Two projects publishing one host port: not documented by Compose (project name, `ports`, and `docker compose up` pages checked). The engine refuses the second bind: the port allocator's error is `Bind for <ip>:<port> failed: port is already allocated` (`daemon/libnetwork/portallocator/portallocator.go`), wrapped as `driver failed programming external connectivity on endpoint <name> (<id>): …` (`daemon/libnetwork/endpoint.go`), which Compose surfaces as `Error response from daemon: …`; the container is created but does not start, so `up -d --wait` fails. `compose.yaml` sets no `restart` policy, so there is no restart loop.

**Source**: https://docs.docker.com/compose/how-tos/project-name/, https://docs.docker.com/reference/compose-file/version-and-name/, https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/, https://docs.docker.com/reference/compose-file/interpolation/, https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/, https://docs.docker.com/reference/compose-file/merge/, https://docs.docker.com/reference/compose-file/volumes/, https://docs.docker.com/reference/cli/docker/compose/, https://docs.docker.com/reference/compose-file/services/ (`ports`), read 2026-10-26 (the pages carry no version stamp; local Compose v5.0.2); https://github.com/moby/moby/blob/master/daemon/libnetwork/portallocator/portallocator.go and `daemon/libnetwork/endpoint.go` at commit `b711d21` (2026-10-22).

**Confidence**: high; medium for the exact wording of the port clash, which was read in source, not reproduced.

## 5. The postgres image (postgres:18)

**Findings**

- "scripts in `/docker-entrypoint-initdb.d` are only run if you start the container with a data directory that is empty; any pre-existing database will be left untouched on container startup." The entrypoint "will run any `*.sql` files, run any executable `*.sh` scripts, and source any non-executable `*.sh` scripts", "in sorted name order as defined by the current locale, which defaults to `en_US.utf8`"; `*.sql` files run as `POSTGRES_USER` (the `postgres` superuser by default) against `POSTGRES_DB`. A failing script makes the entrypoint exit, and a restart against the now initialised directory "will not continue on with your scripts".
- Postgres 18 moved the data directory: `PGDATA` "is `/var/lib/postgresql/18/docker`" and "The defined `VOLUME` was changed in 18 and above to `/var/lib/postgresql`. Mounts and volumes should be targeted at the updated location." `compose.yaml` mounts `postgres-data:/var/lib/postgresql`, which is that location.
- Consequence: `infra/postgres/init/01-vetora.sql` (the three roles, `vetora`, `vetora_test`) runs once per volume, that is once per Compose project name; `pnpm local:down -v` then `pnpm local:up` reruns it, as the file's own comment says.

**Source**: https://github.com/docker-library/docs/blob/master/postgres/content.md, the source of the Docker Hub description, sections "Initialization scripts" and "PGDATA", read 2026-10-26.

**Confidence**: high.

## 6. Vite 8 (vite.dev at v8.3.4)

**Findings**

- Env files in the config: "variables defined in `.env`, `.env.local`, `.env.[mode]`, or `.env.[mode].local` are not automatically injected into `process.env` while your `vite.config.*` is running"; when "values from `.env*` files must influence the config itself (for example to set `server.port`, conditionally enable plugins, or compute `define` replacements), you can load them manually using the exported `loadEnv` helper." Signature: `loadEnv(mode: string, envDir: string, prefixes: string | string[] = 'VITE_'): Record<string, string>`, "Load `.env` files within the `envDir` and merge them with the matching variables already present in `process.env`. By default, only env variables prefixed with `VITE_` are loaded, unless `prefixes` is changed." The docs' own example is `const env = loadEnv(mode, process.cwd(), '')` with the comment "Set the third parameter to '' to load all env regardless of the `VITE_` prefix" and `server: { port: env.APP_PORT ? Number(env.APP_PORT) : 5173 }`. `envDir` defaults to the project root (here `apps/clinic-web`), so a repo root file needs an explicit path. A `''` prefix reads every variable of that file into the config, never into the bundle, which keeps the `VITE_` filter (`envPrefix`); a narrower prefix keeps database URLs out of the config object.
- Ports: `server.port` "Default: 5173. Note if the port is already being used, Vite will automatically try the next available port so this may not be the actual port the server ends up listening on." `server.strictPort`: "Set to true to exit if port is already in use, instead of automatically trying the next available port." CLI: `--port <port>`, `--strictPort`, `-m, --mode <mode>`, `--force`.
- Proxy: `server.proxy` is `Record<string, string | ProxyOptions>`; "Any requests whose request path starts with that key will be proxied to the specified target"; a string value is the target, which is the form `vite.config.ts` uses (`'/api': 'http://localhost:3000'`), so the API port is hard coded there today.
- Cache: `cacheDir` "Default: `node_modules/.vite`" ("pre-bundled deps or some other cache files generated by vite"); pre-bundling reruns when the lockfile, the patches folder, relevant config fields, or `NODE_ENV` change; `--force` or deleting `node_modules/.vite` resets it. Per checkout, because `node_modules` is (observed: `apps/clinic-web/node_modules/.vite/deps`).

**Source**: https://vite.dev/config/ ("Using Environment Variables in Config"), https://vite.dev/guide/api-javascript (`loadEnv`), https://vite.dev/config/server-options (`server.port`, `server.strictPort`, `server.proxy`), https://vite.dev/guide/cli, https://vite.dev/config/shared-options (`cacheDir`, `envDir`, `envPrefix`), https://vite.dev/guide/dep-pre-bundling ("File System Cache"), read 2026-10-26 (site version v8.3.4; the same text in `docs/config/index.md` of vitejs/vite at package version 8.3.5).

**Confidence**: high.

## 7. Node 24 (v24.14.0 docs)

**Findings**

- `--env-file=file`: "Loads environment variables from a file relative to the current directory, making them available to applications on `process.env` … If the same variable is defined in the environment and in the file, the value from the environment takes precedence." "You can pass multiple `--env-file` arguments. Subsequent files override pre-existing variables defined in previous files." "An error is thrown if the file does not exist." Stable since v24.10.0 ("no longer experimental"), added in v20.6.0.
- `--env-file-if-exists=file`: "Behavior is the same as `--env-file`, but an error is not thrown if the file does not exist." Added in v22.9.0, stable since v24.10.0.
- Format: one `KEY=value` per line, `#` comments, values may be quoted with backticks, double or single quotes (quotes dropped), multi-line quoted values, a leading `export` is ignored.
- "relative to the current directory": pnpm runs a package script in that package's directory, so `node --env-file=.env` in `apps/api` reads `apps/api/.env` of whichever checkout runs it; `migrate` and `provision-practice` use `--env-file-if-exists=.env` and tolerate its absence. A shell variable always wins over the file, which is how the AGENTS.md trick `DATABASE_URL_MIGRATOR=… pnpm --filter @vetora/api migrate` works.
- `process.loadEnvFile(path)` (used by `apps/api/vitest.config.ts`): "Loads the `.env` file into `process.env`", default `./.env`, stable since v24.10.0; its page does not state a precedence rule between the file and existing variables.

**Source**: https://nodejs.org/docs/v24.14.0/api/cli.html (`--env-file`, `--env-file-if-exists`) and https://nodejs.org/docs/v24.14.0/api/process.html (`process.loadEnvFile`), read 2026-10-26; local node v24.14.0.

**Confidence**: high.

## 8. lefthook 2.2.2

**Findings**

- Where the hooks go: lefthook asks git `rev-parse --path-format=absolute --show-toplevel --git-path hooks --git-path info --git-dir --git-common-dir` (`internal/git/wrapper/paths.go`) and writes the hook files into the `--git-path hooks` answer and `lefthook.checksum` into `--git-path info`. In a linked worktree both resolve into the common dir (section 1), so one `lefthook install` serves every worktree and an install run from a worktree rewrites the same shared files. `install` compares the config's md5 with `.git/info/lefthook.checksum` (`<md5sum> <timestamp> <hook1,hook2>`, `checkHooksSynchronized` in `internal/command/install.go`) and rewrites only on a change or with `--force`; it refuses when `core.hooksPath` is set ("Run `lefthook install --force` or `lefthook install --reset-hooks-path` once, deliberately, to resolve it").
- No per worktree install is needed: "Reinstall is not required when you modify `lefthook.yml`, the configuration file is read every time a git hook is run", and with `no_auto_install` at its default `false` "lefthook automatically installs and updates hooks when you run `lefthook run` if the configuration has changed". The installed `.git/hooks/pre-commit` (observed, written 2026-10-22) exits 0 when `LEFTHOOK=0`, prefers `LEFTHOOK_BIN`, then `lefthook` on `PATH`, then a hard coded absolute path into the main checkout's `node_modules/.pnpm/lefthook-darwin-arm64@2.2.2/…`, then `$(git rev-parse --show-toplevel)/node_modules/…`. A commit from a worktree therefore runs the main checkout's binary (the same pinned version) with the worktree as working directory, reads the worktree's `lefthook.yml`, and gets the worktree's `{staged_files}`.
- The npm package: "NPM package `lefthook` installs the hooks in a postinstall script automatically"; with pnpm "make sure to update `pnpm-workspace.yaml`s `onlyBuiltDependencies` with `lefthook` … otherwise the `postinstall` script of the `lefthook` package won't be executed and hooks won't be installed" (vetora does); `CI=true` skips the postinstall, `LEFTHOOK=1` forces it even in CI.
- `lefthook-local.yml` "overrides and extends the configuration of your main `lefthook.yml`" (skip a command, wrap it, add `parallel`); the docs suggest listing it in `~/.gitignore`, and vetora's `.gitignore` already ignores it. It is untracked, so a worktree does not inherit the main checkout's copy.
- `LEFTHOOK=0 git commit -am "…"` disables lefthook for one command; `LEFTHOOK_VERBOSE=1` traces the hook script.
- Worktrees: not documented by lefthook (configuration, usage, and installation docs of v2.2.2 checked); the behaviour above follows from the git commands it runs.

## 9. Claude Code worktrees (CLI 2.1.289 in the terminal, 2.1.308 bundled in the desktop app; docs read 2026-10-26, changelog through 2.1.310)

**Findings**

- The flag. `claude --worktree [name]` (`-w`) creates `<repo>/.claude/worktrees/<name>/` "on a new branch named `worktree-<name>`"; without a name "Claude generates one such as `bright-running-fox`". The base is the remote default branch: `worktree.baseRef` is `"fresh"` by default ("branch from the repository's default branch on the remote, usually `main`"; the default branch is fetched when it has not been fetched in 24 hours, capped at five seconds, falling back to local `HEAD` when there is no remote) or `"head"` ("branch from your current local `HEAD`, so the worktree carries your unpushed commits"); "You can't set `worktree.baseRef` to a branch name. To start a worktree from a specific existing branch, create it with git directly." "Passing `--worktree` a name whose directory already exists opens that existing worktree instead of creating a new one" (and under `"fresh"` resets a clean, commit free worktree to the default branch). Interactive runs need workspace trust; `-p --worktree` skips it. `--tmux` requires `--worktree`. `#<number>` or a PR or MR URL branches from that change at `.claude/worktrees/pr-<number>`. Observed: `claude --help` prints `-w, --worktree [name]  Create a new git worktree for this session (optionally specify a name)`, and `claude rm <id>` deletes a background session "and its worktree when that is safe".
- On exit: "The worktree is clean: for an unnamed session, Claude removes the worktree and its branch automatically. A named session prompts you first"; "The worktree has work in it: Claude prompts you to keep or remove the worktree. Keeping preserves the directory and branch … Removing deletes the worktree directory and its branch, along with all the work in them"; a worktree on another branch, or one whose state can't be verified, also prompts. "Non-interactive runs with `-p` have no exit prompt, so Claude doesn't clean up their worktrees, and Claude Code leaves the lock it took on each one at creation in place until a later session's stale-lock sweep releases it." Claude Code "holds a `git worktree lock` on its worktree" while an agent runs and "writes a marker into the git metadata of every worktree it creates with git" (observed: the lock reason `claude session prototype/better-auth (pid 15046 …)` and the `CLAUDE_BASE` file). Resuming a session that ended inside a worktree returns it there; the resume command is printed on exit.
- `.gitignore`: Claude Code does not add `.claude/worktrees/` anywhere; the docs tip is "Add `.claude/worktrees/` to your `.gitignore` so worktree contents don't appear as untracked files in your main checkout." Observed: untracked, and `.git/info/exclude` is the stock template. (Claude Code does write `**/.claude/settings.local.json` into the global excludes file, observed in `~/.config/git/ignore`; that mechanism is not used for worktrees.)
- Tools. `EnterWorktree` "Creates an isolated git worktree and switches into it. Pass a `path` to switch into an existing worktree instead of creating a new one"; a `path` outside `.claude/worktrees/` asks for approval; "From within a worktree session, or from a subagent with a pinned working directory such as `isolation: worktree`, only the `path` form is available and the target must be under `.claude/worktrees/` of the session's repository." `ExitWorktree` "Exits a worktree session and returns to the original directory. Not available to subagents that already run in their own working directory"; it takes `action: "keep" | "remove"` and `discard_changes`, and `remove` deletes the worktree and its branch (Agent SDK TypeScript reference, per the coordinating session).
- Subagents: `isolation: worktree` in a subagent's frontmatter, or `isolation: "worktree"` on the `Agent` call, runs it "in a temporary git worktree, giving it an isolated copy of the repository branched by default from your default branch rather than the parent session's `HEAD`. The worktree is automatically cleaned up if the subagent makes no changes"; "a worktree with changes stays on disk until the periodic sweep below can remove it without losing work". The sweep removes subagent and background session worktrees older than `cleanupPeriodDays` (default 30) but keeps any with changed or untracked files or unpushed commits, any whose session is still a foreground `--worktree` session, and any "You created … yourself with `git worktree add`". "A subagent in its own worktree takes the instruction files it starts with from your main conversation, not from its worktree" and, under `.claude/worktrees/`, "doesn't load the `CLAUDE.md` file or `.claude/rules/` directory at the worktree's root as it reads files there". Subagent commands "run inside its worktree"; a command whose directory resolves to the main checkout fails.
- The hooks. `WorktreeCreate` "Runs when Claude Code creates a worktree": `claude --worktree`, `EnterWorktree`, `isolation: "worktree"` subagents, workflow agents, background sessions, and `claude remote-control` in worktree mode; "A WorktreeCreate hook doesn't run for a worktree Claude adds through Bash" (use a `PreToolUse` hook with the `Bash` matcher for that), and a plugin's hook doesn't run with `--worktree --tmux`. "By default Claude Code creates the isolated working copy with `git worktree`. Configuring a WorktreeCreate hook replaces that default git behavior … Because the hook replaces the default behavior entirely, `.worktreeinclude` is not processed. If you need to copy local configuration files like `.env` into the new worktree, do it inside your hook script." Input: the common fields plus `name`, "a slug identifier for the new worktree, either specified by the user or auto-generated, for example `bold-oak-a3f2`":

  ```json
  {
    "session_id": "abc123",
    "transcript_path": "/Users/.../.claude/projects/.../00893aaf-19fa-41d2-8238-13269b9b3ca0.jsonl",
    "cwd": "/Users/...",
    "hook_event_name": "WorktreeCreate",
    "name": "feature-auth"
  }
  ```

  Output: "WorktreeCreate hooks don't use the standard allow/block decision model. Instead, the hook's success or failure determines the outcome. The hook must return the path to the created worktree directory"; a command hook prints it "as the last non-empty line of stdout. Claude Code strips ANSI escape codes before reading that line … Redirect any other hook output to stderr"; an HTTP hook returns `{ "hookSpecificOutput": { "hookEventName": "WorktreeCreate", "worktreePath": "/absolute/path" } }`. "If the hook fails or produces no path, worktree creation fails with an error"; any non-zero exit fails creation whatever the JSON says; a relative path resolves against the hook's directory; an absolute path with `.`/`..` segments or one passing through a symlink below the repository root is refused. `systemMessage` and `continue` are discarded; no matcher. The docs' example: `bash -c 'NAME=$(jq -r .name); DIR="$HOME/.claude/worktrees/$NAME"; svn checkout https://svn.example.com/repo/trunk "$DIR" >&2 && echo "$DIR"'`.
  `WorktreeRemove` "Runs when Claude Code cleans up a worktree that your `WorktreeCreate` hook created": the keep or remove prompt answered with remove, an unnamed clean session's exit, a background session delete, `ExitWorktree`, and remote control cleanup; "When a subagent or a workflow agent finishes, Claude Code keeps the worktree your WorktreeCreate hook made for it and doesn't run your WorktreeRemove hook." Input adds `worktree_path`, "the absolute path to the worktree being removed" (example `/Users/.../my-project/.claude/worktrees/feature-auth`). The exit code decides: 0 means removed ("make sure your hook deleted the directory"); non-zero with the directory still present means the removal fails "with no git fallback"; JSON output is discarded. "Claude Code never deletes a branch belonging to a hook-created worktree … If your WorktreeCreate hook creates a branch, delete it in your WorktreeRemove hook." Without a remove hook, a hook created worktree that git recognises is removed at exit or `ExitWorktree` "as `git worktree remove --force` would". The docs' example: `bash -c 'jq -r .worktree_path | xargs rm -rf'`. For worktrees Claude Code created itself with git, "Claude Code handles cleanup automatically with `git worktree remove`".
  `SessionStart` has the matchers `startup`, `resume`, `clear`, `compact`, `fork`; its input adds `source` (the same values) and optionally `model`, `agent_type`, `session_title`; only `command` and `mcp_tool` hooks run; plain stdout of a command hook is added to Claude's context (or `additionalContext` in JSON), and the hook can set `initialUserMessage` and the title. It runs in the background at launch, and Claude's first response waits for it.
- Where hooks run and what `cwd` means. "Handlers run in the current directory with Claude Code's environment." After `EnterWorktree`, "`${CLAUDE_PROJECT_DIR}` stays put: it still points at the project root where the session started" and "`cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root after Claude enters a worktree, and the new directory after Claude runs `cd`." "In a worktree session you start from the desktop app, Claude Code reads project configuration such as settings, hooks, skills, agents, commands, and `.mcp.json` servers from the main checkout's root. Hook commands run in that root, and `${CLAUDE_PROJECT_DIR}` points at it. To reach the files Claude is working on, read the worktree's path from the hook's `cwd` input field. `CLAUDE.md` files and `.claude/rules/` still load from the worktree." Permission approvals ("Yes, and don't ask again") are saved in the main checkout's `.claude/settings.local.json` and apply to every worktree (since 2.1.211). Project scope plugins load in worktrees (2.1.200+), and the main checkout's `.claude/skills`, `agents`, `commands` are read through when the worktree has none (2.1.277+).
- `.worktreeinclude` at the project root: "The file uses `.gitignore` syntax. Only files that match a pattern and are also gitignored are copied, so tracked files are never duplicated." The docs' example lists `.env`, `.env.local`, `config/secrets.json`. It "applies to every worktree Claude Code creates with git: `--worktree` worktrees, subagent worktrees, and parallel sessions in the desktop app", not to hook created ones. The copy is verbatim: a copied `apps/api/.env` carries the main checkout's ports.
- Settings (`worktree` object, any settings file): `baseRef` (`"fresh"` | `"head"`); `symlinkDirectories` ("Symlink directories from the main repository into each worktree so you don't duplicate large directories on disk", example `["node_modules", ".cache"]`); `sparsePaths` (git sparse checkout of the listed directories plus root files; "While a sparse worktree exists, git enables `extensions.worktreeConfig` in the repository's shared `.git/config`"); `bgIsolation` (`"worktree"` default: background sessions can't `Edit`/`Write` the main checkout until they call `EnterWorktree`; `"none"` lets them edit in place). `worktree.location` is read by the desktop app for SSH sessions only. The changelog dates them: `--worktree` and `isolation: "worktree"` 2.1.49, `WorktreeCreate`/`WorktreeRemove` 2.1.50, `ExitWorktree` 2.1.72, `sparsePaths` 2.1.76, `EnterWorktree` `path` 2.1.105, `baseRef` 2.1.133, `bgIsolation` 2.1.143.
- Isolation enforcement, every session type: "File edits: Claude Code blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout. Command working directory: Claude Code blocks a Bash, PowerShell, or Monitor command whose working directory resolves to the main checkout, or whose working directory it can't verify stays outside it. Git redirects: … `git -C`, `--git-dir`, a `GIT_DIR` or `GIT_WORK_TREE` variable, or a `cd` into the main checkout before running git. Command shape: Claude Code blocks a Bash or Monitor command when it can't verify from the command text that any git the command runs stays inside the worktree … You can't turn this check off." ## What this means for vetora

- Only four things must differ per checkout: the Compose project name with its two published ports (5432, 8333), the API's `PORT` and `PUBLIC_ORIGIN` in `apps/api/.env`, Vite's port, and Vite's proxy target. Git refs and hooks, the pnpm store, and the Turborepo cache are shared by design and need nothing.
- Compose: `name:` becomes `${COMPOSE_PROJECT_NAME:?…}` and the two `ports` lines `${VETORA_POSTGRES_PORT:?…}:5432` and `${VETORA_S3_PORT:?…}:8333`, with the values in a root `.env` per checkout (already ignored by the `.env` rule; keep a tracked `.env.example`). Compose reads that file because the project directory is the directory of `compose.yaml`, and the `.env` beats `name:` while a shell variable beats the `.env`. A new project name means a new volume, so `01-vetora.sql` runs again and each worktree gets its own `vetora`, `vetora_test`, and roles; the running `vetora` project keeps 5432 and 8333.
- Vite: `vite.config.ts` reads that root `.env` with `loadEnv(mode, <repo root>, 'VETORA_')`, sets `server.port` from it with `strictPort: true` (otherwise Vite slides to 5174 while `PUBLIC_ORIGIN` still says 5173), and builds the `/api` proxy target from the API port. Turborepo's strict `envMode` strips unlisted shell variables from `turbo run dev`, so reading the file is the robust path; a `globalEnv` entry is the alternative.
- API: `apps/api/.env` stays per checkout (`--env-file=.env` is relative to `apps/api`); a copy of `.env.example` must have `PORT`, `PUBLIC_ORIGIN`, and the three database URLs rewritten with the checkout's ports, which rules out a verbatim `.worktreeinclude` copy for it. `pnpm local:down` and `docker compose exec` stay project scoped through the same root `.env`.
- pnpm: `pnpm install --frozen-lockfile` (or `--offline`) in every new worktree is mostly hard links from `~/Library/pnpm/store/v10`. Do not use `worktree.symlinkDirectories: ["node_modules"]`: pnpm's workspace links (`node_modules/@vetora/contracts` is `../../packages/contracts`) resolve from the link's real location, so a worktree would import the main checkout's packages.
- Turborepo: the cache sharing is automatic and welcome (no `.turbo` per worktree, identical inputs hit), with one check to run once: no cached output (`dist/**`, `openapi.json`, `src/generated/**`) may embed an absolute worktree path. If one does, set `cacheDir: ".turbo/cache"` explicitly and sharing stops.
- lefthook: nothing per worktree; hooks and the checksum live in the shared `.git`, a worktree commit runs the main checkout's binary against the worktree's files, and `LEFTHOOK=0` skips one commit. `.git/hooks` and `.git/config` are write denied to sandboxed commands in a worktree session, so `lefthook install --force` and `git config` changes belong in the main checkout.
- `.gitignore` gets `.claude/worktrees/` (Claude Code never adds it). `.worktreeinclude` is for files that can be copied unchanged only; the port bearing files should be generated by a script instead.
- Hooks: a `WorktreeCreate` hook replaces `git worktree add` entirely and switches `.worktreeinclude` off, so it would have to add, lock, and populate the worktree itself and pair with a `WorktreeRemove` hook that also deletes the branch. The lighter seam is a `SessionStart` hook (matchers `startup` and `resume`) that reads `cwd` from stdin, detects a linked worktree with `git rev-parse --git-dir` against `--git-common-dir`, writes the checkout's `.env`, `apps/api/.env`, and `.claude/launch.json`, optionally runs `docker compose up -d --wait`, and prints one line of context; in desktop worktree sessions the hook command runs in the main checkout, so it is addressed as `${CLAUDE_PROJECT_DIR}/infra/<script>` and the worktree is `cwd`. The desktop app creates worktrees in the same place with the same `.worktreeinclude` rules, so one script serves the CLI and the app.
- Cleanup: a kept worktree keeps its Compose project and volumes alive, and neither Claude Code's sweep (`cleanupPeriodDays`) nor the desktop's 30 day removal knows about Docker. Removal is `git worktree remove` (ignored files such as `node_modules` and `.env` do not block it, observed 2026-10-26; `--force` is only for modified or untracked files), `git branch -D` after a squash merge, and `docker compose -p <project> down -v`; a `gc` command that walks `git worktree list --porcelain` and `docker compose ls` finds orphans, and a `locked claude session …` entry belongs to a running session and must not be forced.

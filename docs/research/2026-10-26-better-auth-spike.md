# Better Auth 1.7.12 on Drizzle 1.0.0-rc.5: the feature 5 spike

What the one session `/prototype` detour of 2026-10-26 found, as scoped in `2026-10-24-grilling-next-after-0002.md` ("Feature 5 spike"). The code is the `prototype/better-auth` branch, folder `apps/api/src/platform/prototype-better-auth/` (its README says how to run and wipe it); the branch never merges, this note is what it leaves behind. Everything below was run, not read: the driver's output is the primary source, reproduced by `pnpm --filter @vetora/api prototype:better-auth` against a second compose Postgres (project `vetora-proto`, `postgres:18`, port 5433, a fresh volume, the worktree's `apps/api/.env` pointing at it).

## The question

Does Better Auth 1.7.12 run the way spec 0001 "Auth details" wants it, on this stack: the relations-v2 Drizzle adapter over `drizzle-orm` 1.0.0-rc.5 and Postgres 18, its tables hand written into the `control` schema with UUID v7 ids and `timestamptz`, `transaction: true`, username sign in as `handle@practice-slug`, the organization plugin with the five staff roles and `creatorRole: "manager"`, the admin plugin's `createUser`, TOTP enable and verify, the CLI's schema check, and one Hono request that reads the session cookie and switches to the practice role (spec 0002, "Interface surface": Request transaction).

## What ran

- Versions: `better-auth` 1.7.12 and `@better-auth/drizzle-adapter` 1.7.12 (its `/relations-v2` entry) as dependencies, the `auth` CLI 1.7.12 (`@better-auth/cli` is deprecated) as a dev dependency, all pinned exactly; `drizzle-orm` and `drizzle-kit` 1.0.0-rc.5 untouched; `pg` 8.23, Hono 4.13, Node 24.14, the compose `postgres:18`. `pnpm add` reported no peer problem beyond the pre existing `openapi-typescript` one (the adapter's peer range is `^0.45.2 || >=1.0.0-rc.1 <2.0.0`).
- The config (`auth.ts`): the relations-v2 adapter over `drizzle({ client: pg.Pool, relations: defineRelations(tables) })`, `provider: 'pg'`, `schemaName: 'control'`, `transaction: true`, joins left off (the default); `advanced.database.generateId` a function returning UUID v7, pinnable per model for one call; `emailAndPassword` on; sessions of 12 hours, `updateAge` one hour, cookie cache off; rate limiting on and stored in the database; `username` with a validator for `handle@practice-slug` (handle `[a-z0-9][a-z0-9._]{0,29}`, `@`, the registry's slug shape) and `maxUsernameLength` 95; `admin` with `adminRoles: ['admin']` and `defaultRole: 'staff'`; `organization` with an access control of the five staff roles and nothing else, `creatorRole: 'manager'`, `allowUserToCreateOrganization: false`, `disableOrganizationDeletion: true`; `twoFactor` with `issuer: 'vetora'`.
- The tables (`schema.ts`, applied by `schema.sql`): the nine models (`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, `twoFactor`, `rateLimit`) hand written on the repo's `control` pgSchema object: `uuid` ids and foreign keys, `timestamp with time zone` instants, snake_case columns under Better Auth's field names as the TypeScript keys, one member row per organization and user, `member.role` without the plugin's `'member'` default; SELECT, INSERT, UPDATE, DELETE to `vetora_app`, SELECT to `vetora_backup`, created by `vetora_migrator`. The DDL came out of `drizzle-kit generate --schema schema.ts` and was finished by hand (foreign keys inlined, grants added).
- The walk (`run.ts`): `migrate` (the control set applied to the fresh database), the DDL, a platform admin through a server side `auth.api.createUser` with no session, the admin's username sign in, the first manager through `POST /api/auth/admin/create-user` with the admin's cookie and a pinned user id, `provision-practice` with that id as `managerUserId`, the organization created server side with the practice's id, the manager's sign in, `set-active`, `GET /api/p/:practiceId/whoami` (membership from `control.member`, the registry row, then `set local role`, `set local search_path`, `set_config('app.actor_id')`, a `staff_member` read), the same request for a foreign practice id and without a cookie, TOTP enable and verify with a code computed from the returned URI, sign out, sign in again through the TOTP challenge, whoami again, then row counts, column types and the rows.
- `auth check schema --config …/auth.ts`, once with the database up and once with `DATABASE_URL_POOLED` pointing at port 1; `auth generate --config …/auth.ts --output <scratch>` for the reference schema.

## Findings

1. **rc.5 works with the relations-v2 adapter.** Every operation the walk needed (inserts with returning, single and list reads, updates, deletes, the rate limiter's increments) ran against Postgres 18 through `drizzle-orm` 1.0.0-rc.5 with `transaction: true`, with no error and no adapter warning; the pino log carried no warning or error line. The join path was never taken (joins stay off), so the spike says nothing about `experimental.joins`, and the research note's rc issues (better-auth 10344, 10756, 10297) did not appear.
2. **Hand written uuid and timestamptz tables are accepted.** The runtime check (`advanced.database.validateSchema`, on by default) reported "Drizzle schema mismatch, Missing tables …" against the empty placeholder and nothing against the hand written set; `auth check schema` printed "Schema check passed against the configured Drizzle schema". The dump shows `uuid` on every id and foreign key and `timestamp with time zone` on every instant of the nine tables; Better Auth sent uuid strings and `Date`s and read them back as such.
3. **`generateId` as a function gives UUID v7 everywhere** (`01a174db-d310-7d09-…`, the version nibble 7): users, sessions, accounts, organizations, members, the two factor row, the rate limit rows. Pinning the id per model for one call worked for the user (the manager's fixed id, so provisioning's `staff_member` row matches across reruns) and for the organization (`idsMatch: true`: practice id = organization id, spec 0001 "Tenancy"). The pin is module state, fine in a driver and not in the API: see Open points for where slice 1 should create the organization.
4. **The CLI's generate is a reference, not a file to commit.** It emits `text` ids, `timestamp` without time zone, `pgSchema("control")` from `schemaName`, index names in camelCase, `.unique()` on `organization.slug` twice (the column and a unique index), and a `defineRelationsPart` block in the relations v2 shape. The `.notNull()` omission the 2026-10-24 research predicted did not show for these nine models; every required field carries it. The hand written set differs in the id type, the time zone, a unique member index, and `member.role`'s default.
5. **The CLI loads the repo's config as is, and needs no database.** `--config src/platform/prototype-better-auth/auth.ts` resolved `./ids.js` and `./schema.js` to the `.ts` files (jiti), the `pg.Pool` was created but never connected, and `check schema` passed with `DATABASE_URL_POOLED=postgres://nobody:nobody@127.0.0.1:1/nowhere` as well. So `auth check schema` can run in CI next to `db:check` against the committed `auth.ts`.
6. **The admin plugin creates users server side with no session.** `auth.api.createUser({ body })` without headers skips the session requirement (`routes.mjs`: `if (!session && (ctx.request || ctx.headers)) throw UNAUTHORIZED`), so the break glass script of spec 0001 "Recovery" needs no cookie; the CLI's `create-admin` command exists for the same bootstrap. Over HTTP the call carried the admin's session and succeeded; a staff session was not tried. `data: { username, displayUsername }` lands in the username plugin's columns.
7. **Username sign in as `handle@practice-slug`** passes with `usernameValidator` and `maxUsernameLength`; the plugin lowercases the stored username and keeps `displayUsername`; `POST /api/auth/sign-in/username` returned `{ redirect, token, user }` and the cookie `better-auth.session_token`. Uniqueness across practices comes from the slug suffix. The placeholder email `handle@slug.staff.invalid` passes `z.email()`.
8. **The organization plugin with the five roles.** `ac` plus `roles` replace owner, admin and member entirely; `creatorRole: 'manager'` gave the first member `role = manager`; a server side `createOrganization` with `userId` and no session is a "system action" (`crud-org.mjs`) that bypasses `allowUserToCreateOrganization: false`; `set-active` writes `active_organization_id` on the session row.
9. **TOTP.** `/two-factor/enable` returns `method`, `totpURI` (`otpauth://totp/vetora:<email>?secret=…&issuer=vetora&digits=6&period=30`) and ten backup codes; `/two-factor/verify-totp` with a code from the URI turned `two_factor_enabled` on (the row said `true`, the response's user object still said `false`); the next sign in answered `{ twoFactorRedirect: true, twoFactorMethods: ['totp'] }` with a `better-auth.two_factor` cookie and no session, and `verify-totp` with that cookie issued the session cookie. The enforcement hook for managers was not built.
10. **The request context works as spec 0002 writes it**, on a `vetora_app` pooled connection: membership from `control.member`, the registry row, then `set local role p_<id>_role`, `set local search_path to "p_<id>", ext`, `set_config('app.actor_id', <user id>, true)`, and the `staff_member` row provisioning wrote came back with `roles = {manager}`; `current_user` and `search_path` inside the transaction read as the practice's. A foreign practice id gets 403 before any switch, no cookie gets 401.
11. **Rate limiting in the database works but keys by `no-trusted-ip|/path`.** Better Auth warned that it could not determine a client IP and fell back to one shared bucket per path, and the rows say so. Behind kamal-proxy, slice 1 must set `advanced.ipAddress.ipAddressHeaders` (`x-forwarded-for`) or `advanced.ipAddress.trustedProxies`, or every clinic shares one bucket per endpoint.
12. **The active organization is per session.** After sign out and the TOTP sign in the new session had `active_organization_id = null`, while whoami still worked because it trusts the path's practice id plus membership, which is spec 0001's rule anyway. The request context must not depend on `set-active`.
13. Smaller observations: a credential account's `account_id` is the user id as text; `verification` stays empty without email flows; sign out deleted its session row (three sign ins, two session rows); instants come back in UTC (`2026-10-25T20:58:45.903Z` at 00:58 Baku time), which is domain.md §10's rule.

## The four inputs for the grilling (2026-10-24 record, "Inputs for feature 5's grilling")

- **One username field with a custom validator, or two fields behind a custom endpoint:** one field is enough. The validator is one regex and the plugin's normalisation lowercases the stored value; the sign in screen can still show two boxes and join them. Recommendation: one field.
- **Control tables written by hand versus the CLI's output with edits:** hand written in the control migration set, with `uuid` and `timestamptz`, checked by `auth check schema`; the CLI's output is diffed against them on every Better Auth bump (finding 4).
- **`auth check schema` in CI beside `db:check`:** yes; it needs the committed `auth.ts` and no database (finding 5).
- **rc.5 at runtime:** no issue in the adapter's non join path (finding 1); the join path stays unexercised, and `experimental.joins` stays off.

## Open points the spike raises for the grilling

- Which side issues the practice id: provisioning (the registry row first, then the organization created inside provisioning with that id, through `auth.api.createOrganization` and an id supplied from the API's `generateId`), or Better Auth (the organization first, the registry row inserted with its id, which means `provision-practice` takes an id). Both work with a function `generateId`; a module state pin like the spike's is not for the API.
- `member.role` is one text column (the plugin joins several roles with commas, `parseRoles`) while `staff_member.roles` is an array: the sync rule between them, and whether a member holds several roles in Better Auth or one role plus the mirror.
- The platform `user.role` (`admin` or `staff`, the admin plugin) is separate from practice roles; keep it so (spec 0001, "admin plugin for you only").
- The TOTP requirement for managers is a hook after sign in; `twoFactorRedirect` is already the response shape. PIN switching is untouched by the spike.
- Deployment settings the spike ran without: `advanced.ipAddress` for kamal-proxy, `trustedOrigins` and `baseURL` for the real origin, `useSecureCookies` on, the secret from Kamal.

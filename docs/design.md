# Design: what the code needs from the vetora design system

The vetora design system is a Claude Design System artifact outside the repo (https://claude.ai/artifact/1q8EqTdSMXAx7J2nh7yPYS, also linked from `docs/specs/0001-stack-architecture/rationale.md`): a brand book, the tokens, the Roboto variable font, 121 Material Symbols icons, 53 React components with their stylesheet, seven page and five document examples, and the glossary, voice, messages and formats in Azerbaijani, Russian and English. This file records what the code takes from it and how (feature 4; spec #9; ADRs 0003, 0004 and 0005): who decides each kind of thing, the tokens as CSS variables, the type classes, every component and where it lives, the print sheets, the formatters and the time zone boundary, how words flow, and the ledger of the repo's changes to the component sources. The brand book's prose is not repeated here: the rules themselves are read in the artifact (`project/README.md`, and `project/components/<Name>/README.md` for each component).

## Who decides what (ADR 0003, ADR 0005)

ADR 0003 vendors the artifact's sources into `packages/ui` (`@vetora/ui`), compiled by the repo's TypeScript to `dist/`, linted by Biome and tested by Vitest, on the app's own React 19; the app uses none of the artifact's `bundle.js` (React 18.3.1, `window.Vetora`), `index.d.ts` and `lib/`, though a sync up rebuilds that `bundle.js` from the repo's sources for the canvas. ADR 0005 splits the source of truth by kind from the commit that closed #11 (2026-10-26): a colour, a size, a word, an icon or a page's order of parts is decided in the artifact; how a control behaves is code, and code is the repo's.

| Kind | Decided in | In the repo | Moves by |
|---|---|---|---|
| Tokens (`project/tokens.json`) | the artifact | `packages/ui/src/tokens/tokens.json`, byte for byte; compiled to `packages/ui/styles/tokens.css` | re-copy, then `pnpm --filter @vetora/ui tokens` |

## Tokens: the CSS variables

`packages/ui/src/tokens/compile.ts` compiles `tokens.json` to `styles/tokens.css` by the artifact type's grammar (`artifact-type/reference/format.md`, "tokens.css as compiled", mirroring the compiler the artifact's own page runs); the artifact publishes no token stylesheet, so this is what makes the component stylesheet's `var(--…)` references resolve. Colours and shadows sit under `:root, [data-theme="light"]`, the one theme (the app is light only: `color-scheme: light` in `apps/clinic-web/index.html`, and the compiler fails loudly on a second theme); everything else under `:root`. The output is committed, and `src/tokens/compile.test.ts` fails when it is stale or when the stylesheet reads a variable nothing defines. Use the semantic name (`--primary`, `--text`, `--surface-inverse`), never a brand name or a hex value, so a tuning in the artifact reaches every screen.

## Components

Every component the artifact's index exported at the fork point is compiled from `packages/ui/src/` and exported from `@vetora/ui`, name for name; `packages/ui/src/index.test.ts` holds the list, and the repo's additions beside it. Each component's own rules are in the artifact's `components/<Name>/README.md` (ScheduleKey under Schedule, StatGroup under Stat) and its props in the source's JSDoc. Nothing restyles a component from outside and nothing rebuilds one by hand; the web app's own CSS is layout glue. The clinic components do no clinical or financial reasoning: ranges, due dates and amounts are given to them.

## Pages

Every signed in screen is one of seven pages, each a working example in the artifact (`components/<Page>/preview.html`, with its order of parts in the README beside it), and a new screen starts from the nearest one and keeps that order: `SchedulePage`, `ListPage`, `RecordPage`, `VisitPage`, `FormPage`, `SettingsPage` and `DashboardPage`; before sign in, `SignInPage`. A page is an `AppShell` holding, in order, a header (`PageHeader`, or `PatientHeader` where the page is about one patient), a `PageBody`, and on forms and settings `FormActions`; one h1, in the header; one primary action, in the header or, on a form, in the bar at the bottom. A page that shows data has four states, each looking different from the others: loaded (the content); loading (the frame, the header and every heading at once, a `Skeleton` in the shape of what is coming, the region `aria-busy`, nothing jumping when the data arrives); empty (an `EmptyState` that says what is missing and offers the way forward; filters that match nothing stay, with an offer to clear them); failed (a `danger` `Banner` first in the body that says what could not be loaded and offers "Try again", never an empty list). The status page (`apps/clinic-web/src/pages/StatusPage.tsx`), the first page on the shell, shows three of them: it has nothing to be empty of. After signing in people land on the schedule; until the schedule exists they land on Visits today (`/`, ticket #19), and the status page moved to `/status`, after it in the rail. The sign in page (`SignInPage.tsx`) follows the `SignInPage` example of version 23, and the profile the rail's account entry opens is a settings-like page of its own (`ProfilePage.tsx`). New visit (`NewVisitPage.tsx`, ticket #21), Visits today's primary action, follows the `FormPage` example. From ticket #22 Visits today (`VisitsTodayPage.tsx`) is a `ListPage` holding the day's visits in a `Table`, and the visit page (`VisitPage.tsx`, `/visits/$visitId`) follows the `VisitPage` example. The examples are not components and are not copied (spec #9, "Out of scope"): they are read in the artifact, or handed to a session with "Send to local coding agent".

## Print (ADR 0004)

The print components are compiled with the rest and are the one implementation of each document: drafts and on screen printing go through the browser's print dialog from a `PrintPreview`, as designed, and from feature 14 the API's worker renders the same sheet to a stored PDF with a headless Chromium pinned through Playwright (ADR 0004; `@react-pdf/renderer` is dropped). Nothing renders a PDF today.

| `PrintSheet paper` | The sheet on screen | `@page` rule in `components.css` | Used for |
|---|---|---|---|
| `a4` (the default) | 210 × 297 mm, padding `--paper-margin` 15 mm | `vt-a4`: size A4, margin 15 mm, page numbers "1 / 2" at the bottom right | invoices, certificates, discharge summaries |
| `a5` | 148 × 210 mm, padding `--paper-margin-sm` 10 mm | `vt-a5`: size A5, margin 10 mm | prescriptions |

A document is a `PrintSheet` holding a `Letterhead`, then `PrintSection`s, then a `SignatureBlock`; a receipt is a `PrintSheet` holding one `Receipt`. The browser flow: `PrintPreview` shows the sheets at their real size on a grey ground with the print button and marks the page (`vt-has-preview` on the root element) so that printing it prints the sheets alone; its button sets the document title to `fileName` (the browser names a saved PDF after it) and calls `window.print()`, or `onPrint` in its place. Any page of the app prints as it stands: the rail, buttons, tabs and filters stay off the paper by themselves, `vt-no-print` keeps anything else off, `vt-print-only` shows something only there. Paper has no fills or shadows, tables and badges drop theirs inside a sheet, and a document reads the same from a black and white printer. A document is printed in the client's language, which is often not the app's: the sheet takes `lang`, and its numbers and money the document's locale. The state's own forms (the veterinary passport, controlled medication prescription forms, the fiscal receipt) are not replaced by these documents.

## Formatters: the display layer

The design system's formatters (`packages/ui/src/format.ts`, with the month and weekday names in `dates.ts`) write every date, time, age, duration, number, amount, count and phone number, and sort text, for screens and paper in all three languages without the browser's locale data: Chrome has none for Azerbaijani, and browsers disagree on the Russian and English forms. Nothing calls `Intl` for `az` (`CODING_STANDARDS.md`, "Screen text"). A formatter whose result depends on the language takes a `locale` and otherwise follows the root element's `lang`; the parts of a value are joined with non breaking spaces so a date, an amount or a phone number never breaks across lines. The forms themselves are the artifact's `formats.md`.

**Money** (IN-4; spec 0002 AC-9; `CODING_STANDARDS.md`, "Money and time"): money is stored and carried as integer minor units beside a currency code, and a float never enters storage. `formatMinorUnits` in `packages/ui/src/money.ts`, with `formatMinorUnitsPlain` beside it for a bare table cell, is the one place minor units become a displayed amount, and `parseMinorUnits` beside them the one place a typed amount becomes minor units (Take payment's dialog, #26: the digits moved past the decimal mark, never a float multiplied): it takes a `number` or a `bigint` (how a 64-bit column leaves the database) and the currency, hands the design system's `formatMoney` the amount in manat it expects, and throws rather than show a wrong figure for an amount that is not a whole number of minor units, one too large to show exactly, or a currency the design system has no format for (AZN is the one it has). No other code divides money, and a review checks it; `packages/ui/src/money.test.ts` proves the formats, the sign, zero, a `bigint`, the default locale and the refusals. `InvoiceTable` takes minor units with a `currency` since ticket #25 (`InvoiceLine.price` and `amount`, `InvoiceTotal.amount`, a `number` or a `bigint`) and formats them through the wrapper, its cells bare and its totals with the currency (the ledger below). One gap stands: `Receipt` takes its amounts as manat numbers (`ReceiptLine`, `ReceiptAmount`) and calls `formatMoney` itself, so a screen could feed it only by dividing; before the first receipt screen (fiscal receipts, slice 3; Take payment, #26, prints none) it is changed the same way ("Not yet" below), and until then no screen passes it an amount.

**Time** (`docs/domain.md` §10; spec 0001, "Time and money"): an instant is stored in UTC (`timestamptz`) and shown in the practice's time zone (`Asia/Baku` today, which has observed no daylight saving since 2016; never baked in, since CIS expansion brings other zones). The formatters are not the boundary: `formatDate` reads a `YYYY-MM-DD` string as the day it names and a `Date` through its local getters, and refuses a timestamp string on purpose, because which day an instant falls on depends on the zone; `formatTime` reads a `Date`'s local hours and minutes. So a UTC instant is converted to the practice's wall clock before a formatter sees it, with `date-fns` v4 and `@date-fns/tz` (a `TZDate` in the practice's zone, or a day string computed in it), never with `new Date(instant)` straight from the API; and business dates (the day a visit, a payment or a stock count belongs to) are computed in the API, in the practice's zone, and travel as dates. `date-fns` v4 and `@date-fns/tz` arrived with the first instants on screen (ticket #22): `apps/clinic-web/src/time.ts` holds the boundary, `wallClock()` for an instant and `practiceToday()` for the practice's day, the zone being `/api/me`'s `practice.timeZone`.

**Counts** (ADR 0007): a counted noun's forms live as an object under one key in the translation files, holding what the language needs (`az`: `other`; `ru`: `one`, `few`, `many`; `en`: `one`, `other`), read with `t(key, { returnObjects: true })` and handed to `formatCount`; the translation package's test checks every such object (`packages/i18n/AGENTS.md`). The first dates, times, ages and phones on screen came with ticket #22 (Visits today's times, the visit page's date, age and owner's phone); the first amounts and counts arrive with the invoice (#25) and later screens.
